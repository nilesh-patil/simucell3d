# Release 2.0

**Release 2.0.0** (2026-03-02)

First maintenance release of SimuCell3D after the published 1.0 code. Its changes are also
described, together with the 2.1 changes, in {doc}`v2.1`, where items from 2.0 are marked
*(2.0)*.

:::{important}
2.0 already changes simulation results compared with 1.0, because of the two correctness fixes
listed below.
:::

## Changes

- The project was renamed from DCM to SimuCell3D, and the source layout and build were
  reorganised.
- Adaptive OpenMP scheduling, selected with `--schedule`.
- A faster spatial grid (USPG): the objects of each voxel are stored in a vector instead of a
  linked list.
- Optional sweep-and-prune contact detection (`<contact_detection_algorithm>` in the parameter
  file).
- A per-iteration diagnostics CSV (`--diagnostics-csv=PATH`).
- First correctness fixes, which change results compared with 1.0: the closest-point error in
  the contact distance to a face interior, and the semi-implicit Euler step (with contact model 2,
  1.0 had moved every node with a forward Euler step).
- Memory-safety and robustness fixes: a heap use-after-free in edge splits, division-by-zero
  guards, an integer overflow in the spatial grid, and an oscillation bail-out in the mesh
  refiner.
- The lab's growth benchmark file of 1.0, `parameters_benchmarck.xml`, was removed. This was not
  recorded at the time ({ref}`whatsnew-v2-1-known-issues`).
- GitHub Actions continuous integration with sanitizer builds and benchmark workflows. The test
  suite grew to 294 registered CTest targets.

## Obtaining 2.0

The release is the git tag `v2.0`:

```console
$ git clone https://github.com/nilesh-patil/simucell3d.git
$ cd simucell3d
$ git checkout v2.0
```

It builds with the same commands as 2.1 ({doc}`/install`), with two differences: it declares
`cmake_minimum_required(VERSION 3.0)`, so with CMake 4 add `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`
to the `cmake` line, and it has no `--version` option. That release's own documentation,
re-rendered and not updated, is at <https://www.nilesh42.science/simucell3d/2.0/>.

## Erratum

The `README.md` of the tag `v2.0` contains three wrong statements; the GitHub release notes of
2.0 carry the same correction since 2026-11-18:

- It cites the article with the wrong authors. The correct citation is in {doc}`/citing`.
- It says 2.0 is fully backward compatible and adds no new scientific features. 2.0 changes
  results compared with 1.0 (see above); do not use it to reproduce the published figures.
- Its "build passing" badge was a static image, not the status of continuous integration.

The `CHANGELOG.md` entry of 2.0.0 (and its copy under 2.1.0) also describes the spatial grid
wrongly, as ordered along a Morton curve. The voxels are stored in row-major order
(`include/uspg/uspg_abstract.hpp:126-128`); 2.0 changed only the container of each voxel, from a
`std::forward_list` to a `std::vector` (`include/uspg/uspg_4d.hpp:31`). Morton codes appear only in
a contact-detection class that the solver does not use during a run. The changelog records
released text and is not edited.

## Measured behaviour of 2.0 (November 2026)

The November 2026 benchmark ran 2.0 next to 1.0 and 2.1.0 on 8-core cloud machines (GCP
c2-standard-16, 8 threads) ({ref}`benchmarks`). In short:

- On the lab's growth benchmark (`parameters_benchmarck.xml` of 1.0, contact model 1), every 2.0
  run crashed, with a segmentation fault or an abort, by 216 cells. The cause, stale local cell
  ids after a cell is removed, is fixed in 2.1.
- 2.0 runs the vesicle tension sweep, the two Fig. 3 files for the paper's protocol, the tube and
  the single-cell test files to their end, and the long multilayer file to the 48-hour cap. It
  crashes on the long monolayer file and on the shipped two-cell contact file, and stops with an
  error on a finer-mesh variant of that file. A vesicle run of 100,000 iterations took
  $9.49 \pm 0.79$ hours, against $6.20 \pm 0.95$ hours with 2.1.0 ({ref}`benchmarks-performance`).
- 293 of its 294 tests pass on these machines; the failing one is a timing micro-benchmark.
- 2.0 has no `--threads` option and ignores options it does not know. It derives the thread count
  from the CPUs the process may use, so under `taskset -c 0-7` on a machine with two hyperthreads
  per core it starts only 4 threads; run it without `taskset`.
