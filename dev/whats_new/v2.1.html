Release 2.1#

Release 2.1.0 (2026-11-18)

SimuCell3D 2.1 is a maintenance and robustness release of the code published with Runser, Vetter & Iber (2024) (Citing SimuCell3D). It fixes bugs in the 1.0 physics and mesh code, adds safeguards that keep long growth runs alive, and makes the contact step faster. It adds no new biological model. These notes compare 2.1 with 1.0, the version used in the paper; items marked (2.0) were already part of Release 2.0. The authoritative, complete list of changes is CHANGELOG.md in the repository.

“1.0” means the tag v1.0 (commit 38af451). The Zenodo archive cited by the paper is the earlier commit 5342bf8, with the same source files but contact model 1 instead of 2 as its default (Release 1.0). Measurements marked “reconstructed configuration” come from parameters/longrun_fast_growth.xml, a growth configuration written for 2.x from Table 2 of the paper; it is not the lab’s configuration (see Known issues).

Important

Results differ from 1.0. A simulation run with 2.1 does not reproduce the numbers produced by 1.0. Several 1.0 bugs changed the physics, and fixing them changes trajectories. 2.1 also adds safeguards that delete or repair cells that 1.0 would have kept, or crashed on. To compare with the published figures, re-run the comparison with release 1.0 (Release 1.0) rather than mixing results from the two versions.

Changed behaviour#

The following fixes change simulation results compared with 1.0.

Contact distance to a face interior (2.0)

When a node projected onto the inside of a triangle, 1.0 computed the closest point with one triangle vertex counted twice, so the distance was measured to the wrong point and repulsion missed contacts in face interiors. The closest point is now computed correctly.

Semi-implicit Euler step for all nodes (2.0)

With the full equations of motion (DYNAMIC_MODEL_INDEX 0) and face-face coupling (contact model 2, the default), 1.0 moved every node with its old momentum, whether or not it was coupled across a cell-cell contact. That is an explicit (forward) Euler step, although the paper’s Methods describe a semi-implicit one. The momentum is now updated first, and the new momentum (averaged over a coupled group) moves every node, as in the Methods. For a mode of stiffness \(k\) the 1.0 step acted like a damping coefficient of \(\zeta - k\,\Delta t\), so stiff modes were damped less, or even amplified; every cell surface now relaxes differently, not only the contacts. Contact models 0 and 1 were already semi-implicit in 1.0. See Time integration.

Coupling partner lookup (#113)

The face-face coupling model looked up a node’s partner by the other cell’s global id in a table indexed by local id. After cells had divided the two ids differ, and the partner became whichever candidate a thread visited last. The partner is now the nearest node.

Face orientation after an edge split

When the mesh refiner split an edge, it oriented the new triangles with normals stored on the old faces, which can be out of date. Some new triangles came out inside-out; the affected cell then mis-measured its volume, lost pressure resistance to compression and swelled or stretched. The new triangles now copy the orientation of the face they replace. 1.0 has the same bug.

Division when the cutting plane crosses the surface more than once

If the division plane also cut a thin protrusion of the cell, 1.0 followed only one intersection loop, the division failed and the cell retried at every iteration. Every loop is now traced, the cell is cut along the longest one, and a flood fill that does not cross the cut separates the two daughters; a loop nested inside the longest one is not detected (see Known issues). When the Delaunay triangulation of the cut face does not cover its whole outline, the division is refused and the mother tries again at the next division check; the log line names the cell. See Known issues.

Bending force on sliver triangles

The bending force contains \(1/A\) and \(\cot\theta\) terms and could become more than \(10^6\) times larger than normal on a nearly flat triangle. A hinge is now skipped when one of its two triangles has an area below \(10^{-4}\) times the square of its longest edge, and \(|\cot\theta|\) is capped at 1000. Well-shaped triangles give the same force as before.

Added safeguards#

These mechanisms are not part of the model described in the paper. Each one is logged, so that its frequency in a run can be checked. The user guide describes them in Safeguards.

  • Unstable cells are deleted. A cell is removed if any node coordinate is not a finite number, or if its bounding box is wider than 10 times the cube root of its target volume. Each removal is logged to standard error and counted in the unstable_cells_removed column of the diagnostics CSV.

  • Inside-out and self-intersecting cells are deleted. A cell is also removed if its signed volume is zero or negative, or if its volume exceeds the volume of its bounding box. The log line names the reason (negative volume, volume exceeds bounding box). Static cells are exempt.

  • The mesh refiner gives up on an oscillating cell (2.0; the log message is new in 2.1). When refinement keeps undoing itself at the same place, the refiner stops working on that cell for the current time step, logs it and lets the run continue. Some edges of that cell may stay outside the edge-length bounds until the next step. 1.0 aborted the run with “The refinement of the mesh of cell X failed.”

  • Face orientation self-check. After every mesh refinement each cell checks that its faces are oriented consistently; a cell that fails is logged and re-oriented. The check costs about 0.25% of a time step.

  • The contact grid refuses a diverged domain. If node coordinates are infinite or too large for the spatial grid, the run stops with an error instead of hanging.

  • A cell whose mesh refinement fails is deleted. If refining one cell’s surface throws an error, that cell is removed right after refinement and the run continues. Each removal is logged (Removing cell <id> at iteration <n>: mesh refinement failed: <error>) and counted in unstable_cells_removed. The run still stops on a diverged domain, when out of memory, and when more than max(10, 1% of the cells) fail in one iteration, or all of them do.

Fixed#

  • Crash after a cell was removed: the remaining cells kept stale local ids, which the contact model uses as list indices (segmentation fault at about 2,700 cells in the reconstructed configuration).

  • Race condition in cell division: daughters were appended to the cell list from inside the parallel loop that iterates over it.

  • Heap use-after-free in the edge split of the mesh refiner. (2.0)

  • Division-by-zero guards in matrix inversion and vector angle calculations. (2.0)

  • Integer overflow in the spatial grid (USPG): in voxel indexing (2.0), and in the voxel count of a very large domain, which caused a 20-hour stall.

  • The membrane elasticity energy in the output was always 0.

  • The growth phase in the diagnostics could never be detected.

  • The divisions column of the diagnostics CSV was reset by the 50-iteration scheduling window before it was written every 100 iterations.

  • Face-face coupling under contention: threads read a node’s coupling map while others wrote to it, and a farther partner could overwrite a closer one. The closest-partner rule is now applied under both nodes’ locks.

  • In contact model 2, contact forces added to the nodes of neighbouring cells were lost under contention; they now use an atomic add. Contact models 0 and 1 are not fixed (see Known issues). In a ThreadSanitizer run outside continuous integration (contact model 2, four threads), contact resolution gave 43 race reports before this fix and none after.

  • An error raised during contact detection now reaches the error handler instead of aborting the program with SIGABRT.

  • Undefined behaviour when the solver was destroyed: the contact model base class had no virtual destructor.

  • One damaged cell ended the whole run: an error thrown while refining one cell’s mesh reached the error handler and stopped the simulation (in one 8-core run of the reconstructed configuration at 79,635 cells). The cell is now removed instead.

  • Six error checks never took effect: in the time integration (unsupported combinations of compile-time models) and in the automatic polarizer (an unknown region label), the error object was created but not thrown. These branches are not compiled in the default configuration.

  • A parameter file that is not valid XML was reported as “could not be found … must be an absolute path”. A missing file, an unreadable file and an XML parse error (with its line) are now reported separately; relative paths are accepted, as they always were.

  • scripts/screening_analysis/utils/compute_IoU_euler.py failed with UnboundLocalError when given explicit indexes.

Performance#

  • One OpenMP thread is pinned to each physical core by default. --threads=N overrides the thread count, and SIMUCELL3D_PIN_THREADS=0 turns pinning off. See Parallel performance.

  • Adaptive OpenMP scheduling, selected with --schedule (default adaptive). (2.0)

  • The spatial grid (USPG) stores the objects of each voxel in a vector instead of a linked list. (2.0)

  • Optional sweep-and-prune contact detection, selected with <contact_detection_algorithm>sweep_and_prune</contact_detection_algorithm> in the parameter file; the USPG remains the default. (2.0)

  • Face-face contact uses a compact face grid and splits the work of very large cells across threads. In the measurement reported in the CHANGELOG, with 2,600 cells on 4 threads, the contact step fell from 1,059 ms to 500 ms per iteration. In the November 2026 benchmark this change made the whole run 1.4 times faster on the vesicle and 1.2 times faster on the tube; it had no effect on the lab’s growth benchmark, which uses contact model 1 (Wall time, scaling and memory).

  • The CHANGELOG reports 8-core runs of the reconstructed configuration with release candidates of 2.1 (GCP c2-standard-16, 8 threads). They needed 44-46% less time per iteration at 30,000 cells than the previous development builds, and reached 30,000 cells in about 4 hours. Release 1.0 with only the local-id crash fix needed 28.5 hours. Because the physics also differs, this last comparison is not like-for-like.

  • Measured after release, November 2026, on 8-core cloud machines (GCP c2-standard-16, 8 threads). On the lab’s growth benchmark at 2.5e-8 s, 2.1.0 needs half the wall time of 1.0 with two crash fixes to grow the aggregate to 10,000 cells (\(1.28 \pm 0.01\) h against \(2.53 \pm 0.06\) h). It needs 2.7 times less for 100,000 iterations of the vesicle with growth switched off, 1.7 times less for the tube, and 39% less memory per 1,000 cells (Wall time, scaling and memory). Most of this gain was already in 2.0 and in one later change to contact model 2.

Engineering#

  • The project was renamed from DCM to SimuCell3D, and the source layout and build were reorganised. (2.0)

  • Per-iteration diagnostics CSV (performance_diagnostics.csv, or the path given with --diagnostics-csv=PATH). (2.0)

  • The test suite grew from 126 registered CTest targets in 1.0 to 340.

  • Run launchers live in scripts/runs/; the long-run growth configuration is parameters/longrun_fast_growth.xml, the reconstructed configuration (Tissue growth from a single cell).

  • LICENSE is again the licence text of 1.0, unchanged, and a new NOTICE file states that the changes since 1.0 are copyright Nilesh Patil under the same licence and that 2.x is not reviewed or endorsed by the Iber Lab or ETH Zurich. CITATION.cff names the 2.x maintainer as software author, the article as the preferred citation and the 1.0 archive as a reference (Citing SimuCell3D).

  • simucell3d --version prints the version and the git commit the build was configured from.

  • CMake 3.10 or newer is required, and CMake 4 is supported.

  • Continuous integration builds and tests on GCC 10 (Debian 11, Release) and GCC 13 (Ubuntu 24.04, Release and Debug). It also runs AddressSanitizer and UndefinedBehaviorSanitizer builds, the Python tests and a build of the Python bindings. The long test tier runs on labelled pull requests, on release branches and tags, and on request. Releases follow RELEASING.md, and this documentation is published at https://www.nilesh42.science/simucell3d/ (Continuous integration, Release process).

Known issues#

The items below were known at release. Where the cross-version benchmark of November 2026 measured an effect, it is given under Measured after release; those runs used 2.1.0 on 8-core cloud machines (GCP c2-standard-16, 8 threads) and are described in Benchmarks.

  • Unstable-cell removal has no limit, and a diverged run still exits with status 0 (#118). Unlike refinement failures, unstable cells are removed (removal) without any limit per iteration or per run. In a review run of parameters_vesicle_quick.xml with the time step raised to 5e-7 s, all 432 epithelial cells were removed within 8 iterations and the run exited with status 0. The run total is not printed, removals in the last partial 100-iteration window are not written to the diagnostics CSV, and collect_screening_data.py counts every run with exit status 0 as a success. Count the removals in the standard error of every run (Counting safeguard events) and treat a run with many removals as failed. Measured after release: the shipped parameters/benchmarks/fig3e_monolayer.xml runs to its end and exits with status 0 with 18 of its 434 cells left: 400 were removed as unstable, and 16 more epithelial cells disappeared without a log line. 1.0 stops on the same file with its mesh-refinement error and 2.0 crashes.

  • Cells that fall below the minimum volume are deleted without a log line. This minimum-volume death is part of the model, not a safeguard removal, but no output counts it, in any version; the number of deaths can only be recovered from the cell ids (each division creates two new ids). Measured after release: on the lab’s growth benchmark at 2.5e-8 s, 360,009 cells had died this way by 144,000 living cells, 35.7% of all cells ever created.

  • A division along a nested cut can give interpenetrating daughters (#119). The divider keeps the longest cut loop and does not check whether another loop lies inside it. For a cup-shaped or invaginated cell the interface then spans the cavity: in a review test, 20 of 20 divisions of a cylinder with an axial dimple went ahead this way, the daughters’ total volume exceeded the mother’s by 3.4%, and part of one daughter lay inside the other. Nothing is logged, and both daughters pass the unstable-cell checks. The frequency in growth runs has not been measured.

  • Contact models 0 and 1 can lose contact forces with more than one thread (#120). They add forces to the nodes of neighbouring cells without an atomic add; only model 2 was fixed. These are the two models described in the paper, used by parameters_default_dynamic.xml, parameters_paper_exact.xml (model 1) and parameters_default_overdamped.xml (model 0). Run them with --threads=1, or use model 2. No warning is printed. Measured after release: every growth-benchmark run used contact model 1 on 8 threads and carries this defect. Its size was not measured; repeats agree to within about 2% in final cell count, which bounds the scatter it adds but not a bias.

  • The lab’s benchmark file is unstable at its own time step, and is not shipped (#122). parameters_benchmarck.xml of 1.0 (contact model 1, polarization mode 0, minimum edge length \(6\times10^{-7}\) m) was removed in 2.0 without a note; get it with git show v1.0:parameters_benchmarck.xml (The lab’s benchmark file). Measured after release: at its time step of 1e-7 s, which is also that of Table 2, every version tested is unstable on it. 2.1.0 reached 150,000 cells in 21.7 hours but removed 93,310 cells on the way, the first at 4,800 cells and in large numbers from about 13,800. At 2.5e-8 s, three 2.1.0 runs removed no cell and reached 144,919, 148,914 and 142,314 cells in 48 hours. 1.0 stops with its mesh-refinement error at 126 to 165 cells at every time step tried (Stable time step).

  • The reconstructed configuration is not the lab’s. parameters/longrun_fast_growth.xml differs from Table 2 of the paper in the minimum edge length (\(10^{-6}\) m instead of \(2\times10^{-7}\) m), the lateral surface tension (\(8\times10^{-4}\) instead of \(10^{-3}\) N/m), the basal adhesion and repulsion (0 and \(5\times10^{8}\) instead of \(10^{9}\) Pa/m; without effect with contact model 2), the contact model (2, which the paper does not describe) and 10% standard deviations of growth rate and division volume, which Table 2 does not list (Differences from the paper).

  • Cells interpenetrate in large growing tissues. In long growth runs of the reconstructed configuration, with 2.1 and with 1.0; in that file the contact cutoff (\(2\times10^{-7}\) m) is five times smaller than the minimum edge length (\(10^{-6}\) m). Measured after release: the lab’s benchmark file (contact model 1, cutoff \(5\times10^{-7}\) m) shows it too, in every version that grows past a few thousand cells (1.0 itself stops below 170). The aggregate is a packed tissue up to about 1,000 cells in every run, and up to about 4,000 cells in 2.1.0. Beyond that, its core comes to hold more cell volume than space, because pairs of cells occupy the same place. In one run of 1.0 with two crash fixes this began at about 2,000 cells. 5,000 cells is a working limit. At 136,043 cells, 39% of the cells are superposed in this way (cell superposition). Contact model 1 repels a node only while it is within the cutoff of a neighbouring face, so a superposed pair does not separate again. The vesicle and tube runs (contact model 2) showed no superposed cells in 96 snapshots (Limits of the model).

  • Some divisions are deferred, more often as the tissue grows. In an 8-core run of the reconstructed configuration with a release candidate of 2.1, from 1 to 150,498 cells, 14% of division attempts were refused: 5% below 30,000 cells, rising to 21% between 125,000 and 150,000 cells. A refused mother was refused 1.75 times on average (median 1, at most 31). At a fixed shape some mothers are refused every time until the cell’s shape changes. Measured after release: on the lab’s benchmark file the share is higher, 21% of attempts below 30,000 cells and 27% between 125,000 and 150,000, about 170,000 refusals in a 48-hour run.

  • Rare blow-ups of a few nodes. Occasionally a node is thrown far from its cell in one time step. The unstable-cell safeguard removes the cell and the run continues, but neighbouring cells can be removed with it. The cause is not yet known. Measured after release: the 2.1.0 run of the lab’s file at 1e-7 s removed three cells with two to five non-finite nodes each; none occurred at 2.5e-8 s. A two-cell test case (a variant of params_two_spheres_contact.xml with a finer mesh) loses its mobile cell at iteration 204; whether that is the same defect is not established.

  • The Delaunay step of the divider has no iteration limit. Delaunator::legalize (lib/delaunator/include/delaunator.hpp:450) loops until it finds no edge to flip. Measured after release: two development builds before 2.1.0 hung there on the lab’s file at 1e-7 s; 2.1.0 did not hang in any of its 44 benchmark runs, but the code is unchanged.

  • Daughter cells leak when a division fails after they are created. Each face holds a std::shared_ptr to its cell (include/mesh/face.hpp:55), so a pair of daughters that is discarded when a division fails is never freed. Measured after release: 129-140 KiB per failed division; three development builds before 2.1.0 filled the 61.6 GiB of the machine within 48 hours. 2.1.0 refuses the divisions that failed there at an earlier step, which avoids the leak in practice without fixing it: it held 18.9 GiB at 145,000 cells.

  • The ECM shell of the vesicle does not confine a growing tissue. The ECM of fig_3_vesicle.vtk is a static rigid surface. Measured after release: in the shipped multilayer file run for the paper’s protocol, 25-30% of the cells end with more than half of their nodes outside it, and 98-100% late in the full-length run, in every version (Monolayer and multilayer epithelia).

  • Unchecked lookups in noexcept functions. A few edge and face lookups on the mesh refiner’s path still end the program with SIGABRT if a mesh is damaged.

  • Stale coupling links. When a node switches to a closer coupling partner, its old partner keeps a link back to it until the coupling maps are rebuilt. Present since 1.0.

  • Runs are not bit-reproducible. Two runs with the same input can give slightly different results. This holds even on one thread when a run uses the initial triangulation, divides cells or draws growth rates or division volumes with a non-zero spread. Measured after release: multi-cell runs differ between repeats in every version. Two sources were found. One is a random generator seeded from the wall clock, which places the points of the initial triangulation and of every division interface. The other, where nothing random is drawn, is the threaded accumulation of contact forces (not isolated). Scalar readouts repeat to about 0.1-1%. Only the single-cell analytic test cases, which use neither the initial triangulation nor division, gave identical statistics in every 2.x build (Reproducibility).

  • Unknown command-line options are ignored. simucell3d silently ignores an option it does not recognise, for example a misspelt --thread=4.

  • The Python module has no tests of its own. Continuous integration builds the Python bindings and imports the module, but does not run a simulation through it.

  • The bending force is not an exact gradient (#121). Two defects in the gradient of the hinge angle, present since 1.0, make the bending force deviate from the gradient of the bending energy: the cotangent terms of the second face use the normal of the first, and the edge direction follows the node ids rather than the face winding. On a test sphere the force is on average about 1.5 times the gradient, but with a relative residual of 0.26 to 0.40 that grows with the fold angle and depends on node numbering. With both defects fixed it would be exactly 1.5 times the gradient. 2.1 leaves the force unchanged so that results stay comparable with 1.0.

  • Bending prefactor and bending_energy. The code uses a prefactor of 3 where the paper’s Methods use 2. The code’s 3 matches the bending term of Eq. (1) on regular meshes; the Methods’ discrete formula leaves out a factor 3/2, and so does the bending_energy written to the output, which is about 2/3 of the Eq. (1) term. Unchanged since 1.0. See Cell mechanics.

Upgrading from 1.0#

  • The executable is still build/simucell3d, and a 1.0 command line (./simucell3d <parameter file>) is still accepted. Parameter files moved from the repository root (1.0) to parameters/core/, so 1.0 commands such as ./simucell3d ../parameters_default_dynamic.xml need the new path (../parameters/core/parameters_default_dynamic.xml).

  • The XML tags of 1.0 parameter files are still read. The optional tag <contact_detection_algorithm> is new in 2.0 (Parameter file reference).

  • OMP_NUM_THREADS no longer sets the thread count; use --threads=N (Running simulations).

  • Expect different trajectories (see the note at the top of this page), and check the standard error log and the unstable_cells_removed column for safeguard actions.
